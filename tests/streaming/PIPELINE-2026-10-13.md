# Pipeline optimization follow-up — 2026-10-13

This pass removes additional avoidable input and recovery delays after the
initial stutter fixes. Comparison baseline:
`5af589b66f24b1f6bb72586039adee30ba76cab2`; candidate: the accompanying changes.
Environment: Linux, four-vCPU quota, no GPU device. Aggregate simulation results
are in [pipeline-2026-10-13.json](pipeline-2026-10-13.json).

## Demonstrated defects and changes

- Duplicate input sequences were accepted. Dual-path relative mouse events
  could apply twice, consume twice the rate credit, and prolong a held key's
  watchdog lifetime. Strict freshness rejects duplicates before rate admission
  and watchdog refresh, including sequence wraparound.
- Client input waited for the datagram write before starting the reliable copy.
  Both now start independently, completion follows the first successful write,
  and backpressured datagrams do not accumulate redundant input copies.
- Queued reliable input could publish after session handover. Dedicated-stream,
  control-stream and datagram input now share an ownership check held through
  publication. A real QUIC test keeps the incumbent drainable during handover.
- Dense host NACKs rounded fractional refill credit to zero. The same 300/s,
  300-burst budget now retains fractions: 500 requests spaced 2ms apart receive
  approximately 300 repair credits per second rather than starving.
- Two-row FEC skipped pairs involving the short final fragment. It now restores
  both missing fragments and trims padding using the wire total length, avoiding
  a repair round trip. Tests cover two-fragment, aligned and partial groups,
  different fragment widths, and parity preceding other groups' data.
- Releasing a repaired frame plus its held successors together contaminated
  playout jitter measurements. The decoder now samples accepted original
  arrivals before reorder release and resets playout state for a new stream.
  The deterministic 120fps regression changes artificial pacing from 40ms to
  at most 2ms after a single 200ms-late repair. This does not remove real jitter.
- First NACK deadlines now use both RTT and measured healthy assembly spread.
  On a calibrated 40ms RTT/short-spread route the first deadline changes from
  105ms to 55ms. New/unknown connections retain the conservative 150ms deadline.
  A low-RTT route with a 120ms jitter tail does not flood premature repairs.

The new duplicate-action/watchdog, blocked-input, handover, pacing and tail-FEC
regressions were observed failing before their fixes. There is no additional
fixed playout buffer, and the host's repair ceiling is unchanged.

## Matched deterministic comparison

Seven profiles × 60/120 fps × three seeds × 60 virtual seconds: 42 runs per
revision, using the same updated harness. This version models a 300/s repair
budget, the old/new refill arithmetic, and a data-only resend cache. Therefore
these numbers should be compared within this table, rather than directly with
the earlier report's model. Minimum admission and maximum gap are the worst of
six runs per profile. Admission ends at the decoder ordering gate.

| Profile | Admission before → after | Maximum admission gap before → after |
| --- | --- | --- |
| LAN | 100% → 100% | 16.7ms → 16.7ms |
| Wi-Fi jitter | 100% → 100% | 34.2ms → 34.2ms |
| 1% erasure | 100% → 100% | 154.7ms → 129.5ms |
| 5% erasure | 99.89% → 99.97% | 305.5ms → 243.6ms |
| WAN | 100% → 100% | 298.6ms → 290.9ms |
| Burst | 99.89% → 99.89% | 76.7ms → 76.7ms |
| One-second outage | 97.75% → 97.75% | 1371.8ms → 1371.8ms |

Worst 5%-loss admission age p95 changes from 186.8ms to 136.5ms; maximum held
frames changes from 34 to 32, below the 64 cap. Partial assemblies peak at nine,
below the 24 cap. No loss/WAN run resyncs. The worst 5%-loss NACK count increases
from 825 to 858 per minute; the gain includes earlier repair requests.

The model checks every payload byte, reference-chain order, progress and bounded
queues. It does not model a bandwidth cap, real QUIC congestion, game encoding,
audio or display scanout. Synthetic keyframes also use v4 loss/FEC here, whereas
the live host normally sends them reliably. Exploratory larger-frame runs
showed that extreme loss can still exceed bounded repair capacity; these fixes
cannot make arbitrary offered traffic fit a constrained link.

## Browser and hardware limits

Real WebCodecs/canvas diagnostics were repeated with pacing off/on at 640×360/60,
1080p60 and 1440p120. All produced visible frames without decoder/page errors.
High-resolution software playback varied substantially between repeats, and
1440p120 did not sustain its target. These runs support functional behavior;
they cannot substantiate a hardware FPS gain or Moonlight latency parity.

The initial concurrent browser suite passed 31/33 cases: the recovery case
decoded past its progress floor but presented 145 frames against a 150 minimum,
and a simultaneous dashboard action timed out. Browser checks now default to
one worker to isolate software playback; the assertions remain unchanged.

`npm run test:receiver` measures reassembly CPU with fixture generation outside
the timed section. It checks exact reconstruction under a fixed FEC loss pattern.
Its wall-clock timing is diagnostic, not a throughput or sustained gaming claim.
